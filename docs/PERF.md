# 推理性能实测与容量建议

> 数据来自本地开发机实测，用来说明**趋势与瓶颈位置**，绝对值以你的部署机为准。
> 复现脚本见 `tools/bench/bench.sh`，测试图由 `tools/bench/TextImg.java` 生成。

## 1. 测试环境

| 项目 | 值 |
| --- | --- |
| CPU | 20 vCPU（Windows，32GB 内存，另有 Docker/WSL 常驻占用） |
| 产物 | CPU 版（`flavor=cpu`），本机虽有 GTX 1080 但未使用 |
| 被测接口 | `POST /word/json`（PP-OCRv4 检测 + 识别） |
| 测试图 | 1200×800 PNG，6 行英文，67KB |
| 启动参数 | `-Xms1g -Xmx2g`，预热开启 |

## 2. 结论一：只加载模型不够，必须跑一次空推理

同一进程、同一张图，串行请求的耗时（单位 s）：

| 预热方式 | 第1次 | 第2次 | 第3次 | 第4~10次 | 稳态 |
| --- | --- | --- | --- | --- | --- |
| 仅加载模型 | 3.30 | 3.34 | 2.89 | 2.27 / 7.81 / 6.18 / 4.29 / 4.33 / 5.31 / 1.86 | 0.64（第 11 次起） |
| 加载 + 空推理 | **0.96** | 0.67 | 0.69 | ≈0.68 | 0.66 |

原因：模型加载（`ZooModel`）之后，仍有一次性的 **JIT 编译、算子首次初始化、OpenCV 路径首次调用**，
它们摊在前十几个请求上，与"模型是否已加载"无关。`vision.inference.warmup.predict=true`（默认）
会在加载后对每个模型用自造测试图跑一次完整 `predict`，把这段路也走热。

代价：预热总耗时从约 2.2s 增加到约 3.9s（后台线程，不影响端口就绪）。

## 3. 结论二：真正限制吞吐的是单请求 CPU 量

6 次串行请求的进程 CPU 时间统计：

| 指标 | 值 |
| --- | --- |
| 墙钟耗时 | 4.39s（单请求约 0.73s） |
| 进程 CPU 时间 | 41.58s |
| 单请求 CPU 时间 | **6.93 CPU·s** |
| 平均占用核数 | **9.5 核 / 请求** |

也就是说：一个 OCR 请求会把约 9.5 个核跑满 0.73 秒。
20 vCPU 上理论吞吐上限 ≈ 20 / 6.93 ≈ **2.9 req/s**，实测稳态 1.5~1.8 req/s（约 50~60% 效率，
其余损耗来自上下文切换、GC、上传/落盘）。

这个数字比"并发调优"重要：**CPU 推理的吞吐天花板由单请求 CPU 量决定，改线程数只能改变排队方式，
改不了总工作量**。

## 4. 结论三：并发下的耗时（线程数干预对比）

`POST /word/json`，每轮 12 个请求：

| 并发 | 默认线程数（=20）平均 / P95 | `-Dvision.inference.threads=6` 平均 / P95 |
| --- | --- | --- |
| 1 | 0.70 / 0.73 | 0.71 / 0.74 |
| 4 | 1.50 / 2.04 | **1.30 / 1.67** |
| 6 | **1.81 / 2.61** | 2.10 / 2.49 |
| 8 | **1.53 / 1.98** | 2.19 / 2.55 |

- 单并发不受影响（0.70 对 0.71），说明限制线程不会拖慢正常请求；
- 4 并发时有限制更好，6~8 并发时反而不如默认；
- 样本量小（每档 12 次），差异在噪声范围内，**在本机没有得出"限制线程更快"的结论**。

因此默认值保持 `0`（不干预）。这个开关的价值在另一类机器上：核数远多于并发
（如 64 核只跑 4 个并发）、或一台机器上跑多个实例/多个服务抢 CPU 时，
把每个请求的并行度压下来能让 P95 更稳。是否开启请在目标机上用同一套压测脚本实测。

## 5. 部署建议

1. **堆内存显式指定**：不限制时 JVM 按 1/4 物理内存取 `-Xmx`，实测进程私有内存涨到 4.3GB，
   在内存紧张的机器上被换页后，单请求从 0.7s 退化到 2s 以上。建议 `-Xms1g -Xmx2g`
   （模型常驻的是堆外内存，约 280MB，与 `-Xmx` 无关）。
2. **按单请求 CPU 量规划实例**：单实例（20 核）约 1.5~1.8 req/s。需要更高吞吐就加实例，
   而不是调线程数。
3. **吞吐要求高就走 GPU**：`mvn package -Dgpu=true`，语义不变、代码不变，
   只是把上述 6.93 CPU·s 换成 GPU 时间。
4. **就绪探针看 `warmup.state`**：`/system/status` 返回 `inference.warmup.state=完成` 后再放流量，
   可保证第一个真实请求就落在稳态耗时。
